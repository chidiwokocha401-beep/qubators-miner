Qubators Cloud Miner — Backend Architecture

Covers: live market data proxy, accounts/progress persistence, and leaderboard.

1. Architecture overview

flowchart LR
  A[Web App] -->|GET /api/market-data| B[Backend API]
  A -->|GET/POST /api/progress| B
  A -->|GET /api/leaderboard| B
  A -->|Auth| C[Supabase/Firebase Auth]
  B -->|cached fetch every 60s| D[CoinGecko API]
  B -->|cached fetch every 60s| E[mempool.space API]
  B --> F[(Database)]
  C --> F

The frontend never calls CoinGecko/mempool.space directly — it always goes through your own backend, which caches responses. This avoids rate limits, hides nothing sensitive (these are public endpoints), and gives you one place to fix a broken upstream API later.

2. Database schema (Postgres via Supabase, or equivalent)

users (mostly handled by Supabase Auth automatically)

  • id (uuid, PK)
  • email
  • display_name
  • created_at

progress

  • user_id (FK → users.id)
  • stage_id (text: "stage1" | "stage2" | "stage3")
  • completed (bool)
  • completed_at (timestamp)
  • quiz_score (int, optional)
  • Primary key: (user_id, stage_id)

farm_config (optional, if you want to persist their rig selections)

  • user_id (FK)
  • rig_ids (jsonb array)
  • updated_at

leaderboard_cache (materialized/denormalized for fast reads)

  • user_id (FK)
  • display_name
  • metric (e.g. total hash rate, or completion time in seconds)
  • rank (computed on read or via scheduled job)

market_data_cache

  • key (text: "btc_price" | "difficulty" | "network_hashrate")
  • value (numeric)
  • fetched_at (timestamp)
  • Backend checks fetched_at; if older than ~60s, refetch from upstream, else serve cached row.

3. API routes

Route Method Purpose
/api/market-data GET Returns cached { btc_price, difficulty, network_hashrate, fetched_at }
/api/progress GET Returns current user's progress across all stages
/api/progress POST Body { stage_id, completed, quiz_score } — upserts one stage's progress
/api/leaderboard GET Returns top N users by chosen metric, paginated
/api/certificate GET Returns completion status + generates certificate data once all 3 stages done

Auth: attach the Supabase/Firebase session token on every request; backend verifies it before touching progress or leaderboard for that user. market-data can be public/unauthenticated.

4. Live data refresh strategy

  • Run a scheduled job (cron, every 60–120s) OR refresh lazily on request if cache is stale — either works at this scale.
  • Never let the frontend poll the upstream APIs directly.
  • Store a fetched_at timestamp and show it in the UI ("data as of HH:MM") so users understand it's a snapshot, not real-time tick-by-tick.

5. Leaderboard computation

  • Recompute ranks on a schedule (e.g. every 5 min) rather than on every read — cheaper and avoids leaderboard "flicker."
  • Use a privacy-safe display_name, never real email/name, shown publicly.

6. Suggested build order

  1. Wire up Supabase/Firebase auth (email/password + optional Google login)
  2. /api/progress GET/POST + progress table — replaces the current localStorage-only version
  3. /api/market-data with caching — replaces hardcoded sample numbers in the app
  4. /api/leaderboard — last, since it depends on progress data existing first
